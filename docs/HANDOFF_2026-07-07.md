### 4.2 Adaptive runtime budget

New file:

- `scripts/runtime_budget.py`

Purpose:

- keep all major modules online if possible
- reduce runtime pressure as the scene grows

Current default adaptive policy:

- visualization interval:
  - stage 0: every `10` frames
  - stage 1: every `20` frames
  - stage 2: every `30` frames
- loop trigger interval:
  - stage 0: every `6` keyframes
  - stage 1: every `9` keyframes
  - stage 2: every `12` keyframes
- mapper iterations:
  - stage 0: base iterations
  - stage 1: about `67%` of base
  - stage 2: about `40%` of base

Stage switching uses:

- dataset progress thresholds: `0.45`, `0.75`
- keyframe thresholds: `120`, `220`
- gaussian count thresholds: `150000`, `300000`

### 6.2 Full Hotel combo run

The most important confirmed full-combo runtime result is:

- log: `/home/jetson/VINGS-Mono/output/hotel_fullcombo_2026-05-28_05-49-33.log`
- progress reached: `342/405`
- failure point: online visualization

Confirmed failure signature:

- repeated `NvMapMemAllocInternalTagged ... error 12`
- final crash:
  - `torch.cuda.OutOfMemoryError`
  - attempted allocation around `1.08 GiB`
  - stack landed in `scripts/gaussian/vis_utils.py` via `self.vis_map_fn(...)`

Interpretation:

- the full pipeline got much further than the earlier smoke tests
- the blocking issue at that point was not `save_ply`
- the blocking issue was not a clean loop-only failure
- the actual late-stage failure was `vis_map` rasterization pressure as gaussians and trajectory history grew

### 6.3 Adaptive runtime smoke attempts

After adaptive runtime scheduling was added, short Jetson smoke runs were attempted.

Observed issues in those short runs:

- `NvMapMemAllocInternalTagged ... error 12`
- `RuntimeError: cuDNN error: CUDNN_STATUS_NOT_INITIALIZED`

These smoke attempts failed too early to count as a clean validation of the adaptive scheduler itself.

Likely interpretation:

- the Jetson was in a fragile resource state
- unified memory / swap pressure or resource fragmentation was likely involved
- these failures happened before a meaningful full adaptive rerun could be evaluated end-to-end

## 7. Current Known Risks / Open Issues

### 7.1 Online visualization is still the largest confirmed late-stage blocker

Even with the rest of the stack running, `vis_map` can still become the dominant OOM trigger in later frames.

### 7.2 Metric path warning still exists

You may still see:

```text
NO pretrained imagenet ckpt available! Check your path!
```

This appears to come from Metric3D attempting to load an additional backbone pretrain from a hardcoded upstream path. It is not the same as the main `metric_depth_vit_small_800k.pth` being missing.

### 7.3 Some working-tree noise remains on Jetson

Untracked entries still present in the main repo:

- `data/`
- `reports/`
- strange filenames such as `2` and `\`

Also, `submodules/metric_modules` still has dirty `__pycache__` files:

- modified `.pyc`
- untracked `.pyc`

These should be cleaned or ignored before any push or migration packaging step.

### 7.4 Mounted Windows path is not a reliable Git control surface

Source files are readable and writable from the mounted path, but `.git` access can fail. Use SSH into Jetson for branching, staging, and committing.

## 8. Recommended Next Steps

Recommended order for the next owner:

1. Clean repo hygiene first
   - ignore or remove `__pycache__`
   - decide what to do with stray root files (`2`, `\`)
   - keep `data/` and `reports/` out of source control
2. Re-run on a clean Jetson session
   - preferably after reboot
   - avoid extra desktop/GPU load
   - verify memory baseline before launching
3. Re-test the Hotel path with adaptive runtime enabled
   - start with current wrapper defaults
   - capture a fresh log
4. If full-combo still fails late
   - reduce `vis` frequency even further
   - consider switching to delayed / sparse vis only
   - keep `save_ply` final export separate from online vis
5. If failures move earlier into metric or frontend
   - make metric sparse or budget-driven
   - investigate cuDNN initialization fragility on Jetson
   - re-check unified memory pressure and background processes
